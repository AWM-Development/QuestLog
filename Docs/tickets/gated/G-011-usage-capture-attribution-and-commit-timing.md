# G-011 — Usage-capture artifact: reliable session→ticket attribution and commit timing

Gate type: 🧠 strategy

Milestone ref: Docs/milestones/MILESTONES_V1_2_MCP.md § M-OBS.1 (T-046, shipped) — this is a design gap discovered in the shipped feature, not an unticketed milestone task; M-OBS.1's checkbox stays `[x]`, this gate covers the fix.

Opened: 2026-07-27 — by Alex during a ticket-writer planning session, from two bugs Alex reported directly (not yet ticketed or investigated live in-session beyond reading the affected source).

Context files (load ONLY these):
  - packages/core/src/observability/capture-usage.ts (`captureUsage`, `resolveTicketIdFromRepo` — the guess-based attribution and the overwrite-on-write artifact path)
  - packages/core/src/observability/usage-summary.ts (`resolveTicketId`, `resolveArtifactPath` — the heuristic and the ticket-id-keyed, non-session-scoped filename)
  - .claude/hooks/stop-usage-capture.sh (the Stop hook itself — what it has access to: `CLAUDE_PROJECT_DIR`, stdin payload, shell/git access)
  - Docs/tickets/EXECUTOR_ROUTINE.md Step 2 (branch/ticket setup, the natural place to write an explicit marker if that's the chosen approach), Step 7 (the "if the artifact exists, commit it" instruction this gate makes obsolete or reworks)
  - Docs/tickets/done/T-046-executor-usage-capture-hook.md and Docs/tickets/reports/T-046-executor-usage-capture-hook.md (original design intent and reviewer notes)
  - Live evidence in this repo right now: `Docs/tickets/cost-reports/` currently holds three untracked, uncommitted `.usage.json` files (`T-046`, `T-049`, `T-060`) sitting in the working tree unattached to any commit — a real-time instance of Bug 1

Open question: How should the executor positively signal "this session is doing real work on ticket T-###, please attribute and persist this artifact" — replacing the current after-the-fact guess (last 5 commit subjects, else newest file in `done/`/`blocked/`) — **and** how/when should the resulting artifact actually get committed, given that in a fully autonomous run the Stop hook doesn't fire until after Step 7 (PR-open) has already completed? These two questions are coupled: whichever mechanism supplies reliable attribution also has to fit into a commit path that doesn't depend on the hook firing before the PR opens. Candidate directions to weigh (not exhaustive, no direction pre-selected):
  1. **Hook self-commits.** The Stop hook already `cd`s into the project dir and has shell access — have it `git add`/commit (and optionally push) the artifact directly onto whatever branch is currently checked out, immediately after writing it, instead of relying on Step 7 to find it. Needs a decision on: does it push automatically, and what happens on a branch with no ticket context (a stray commit no PR will ever include)?
  2. **Explicit breadcrumb.** Step 2 of `EXECUTOR_ROUTINE.md` writes a small marker file (e.g. `.claude/.active-ticket`) naming the ticket it's about to work on the moment it creates the branch; `capture-usage.ts` reads that marker instead of guessing, and Step 7 (or the hook) clears/removes it at wrap-up. Solves attribution (Bug 2) directly; still needs pairing with a commit-timing fix for Bug 1.
  3. **Session-keyed artifacts + reconciliation.** Key every artifact by `session_id` (never by ticket id) under `Docs/tickets/cost-reports/sessions/<session_id>.json`, never overwritten; add a reconciliation step (part of Step 7, or a separate script) that scans session files created since the ticket's branch was cut and merges/selects the relevant one(s) into the final per-ticket file. Eliminates the overwrite risk in Bug 2 entirely; still needs pairing with something that fires that reconciliation before/at PR-open time rather than after.

Blocks: none yet — Scope can't honestly be written until this decision lands; the concrete fix (and therefore any ticket's Scope/Exit condition) depends entirely on which direction above (or another) is chosen. No ticket drafted.

Notes: Two related but distinct bugs motivate this gate, both confirmed by Alex directly (not independently reproduced by ticket-writer beyond reading the source above):
  - **Bug 1 (commit timing):** in a fully autonomous nightly run, Steps 0–7 of `EXECUTOR_ROUTINE.md` execute inside one continuous turn with no Stop-hook fire until the turn ends — so Step 7's "if the usage artifact exists, commit it" instruction (line 84) never finds it; the artifact is written to disk only after the PR is already open, and every subsequent turn in that session (including unrelated follow-up questions) re-fires the hook and rewrites the same orphaned, uncommitted file. Observed directly: recurred four times in the T-049 session referenced during planning (had to be manually committed/pushed three separate times), and is reproducing live right now — see the three untracked files in `Docs/tickets/cost-reports/` noted in Context files above.
  - **Bug 2 (attribution/overwrite):** `resolveTicketIdFromRepo()` (`capture-usage.ts:84-111`) has no way to know whether the *current* session actually did ticket work — it answers "what's the most recent ticket in this repo," not "what did this session do." Any session at all (including a read-only `/morning-review`) triggers the same Stop hook, resolves the same "most recent ticket," and `writeFileSync`s over `Docs/tickets/cost-reports/T-###.usage.json` — a full overwrite keyed by ticket id only, no session id, no versioning. Confirmed concrete damage: a read-only `/morning-review` session (session `92c35482-...`, $0.6483, `turns_to_green: 13`) overwrote and destroyed T-049's real executor-run record (session `dbb17830-...`, 22 turns, $0.6203, `turns_to_green: 14`).
  - Alex's explicit call during planning: these two bugs should be resolved together under one gate rather than as two independent tickets, because any fix to Bug 1's commit-timing problem has to be compatible with whatever fixes Bug 2's attribution problem (e.g. a hook that self-commits based on the *same* unreliable guess Bug 2 identifies would just commit corrupted data faster, not fix anything). Mechanism has not been pre-selected — to be decided fresh in the `/ungate` session from the three candidate directions above (or another that surfaces there).
