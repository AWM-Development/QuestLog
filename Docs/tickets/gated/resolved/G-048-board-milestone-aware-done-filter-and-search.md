# G-048 — Board: milestone-aware Done filter + milestone search

Gate type: 🧠 strategy + 🎨 design

Milestone ref: M-OBS.9

Opened: 2026-08-22 — by Alex during `/ungate`'s resolution of `G-043` (ticket-board visual design), two requests raised together while reviewing the read-only board mockup: (1) the Done column should only show tickets belonging to a milestone that's currently in-progress — a fully-completed milestone's shipped tickets, or an unstarted milestone's (none, trivially), shouldn't clutter Done; (2) the column's "+N earlier" overflow affordance should open a milestone search module — initially populated with clickable milestones, searchable by milestone or ticket, that on selecting a milestone shows its full ticket breakdown (completed and outstanding, in order). Alex flagged this as scope beyond a visual-only gate and asked whether `board.list`/its sibling endpoints could reasonably support it — this gate exists to answer that combined with the visual design, the same way `G-047` was split out for the writable-board ask.

  - Docs/tickets/TICKET_SPEC.md § "Milestone-doc annotations" (how a ticket's milestone-doc line is tagged today — relevant to whichever aggregation approach this gate picks)

Open question: How does "in-progress milestone" get computed, and what does the milestone search surface actually query?
  - **Status derivation**: is a milestone's status (unstarted / in-progress / completed) derived from the milestone doc's own checkbox lines (`- [ ]`/`- [x]`), from aggregating every ticket file's folder-derived status across the milestone's referenced `T-###`/`G-###` ids, or some combination — and what happens when the two disagree (e.g. a checkbox is stale)?
  - **New query surface**: does `board.list` grow a `milestoneRef` + milestone-status field per ticket (cheap, reuses the existing read), or does this need a dedicated `milestone.list`/`milestone.get` endpoint that returns full per-milestone task breakdowns for the search module — and if the latter, does it live beside `board.list` in the same tRPC router T-157 stands up, or is it its own ticket?
  - **Search scope**: milestone search matches milestone id/name — should it also fuzzy-match ticket id/title within a milestone (as the mockup does), and if so is that a client-side filter over an already-fetched milestone+task list, or a server-side search query? Given the read-only ops-tool nature and likely small milestone/ticket counts, client-side filtering over one bulk fetch is probably sufficient — but this gate should say so explicitly rather than leave it implicit.
  - **Done-column cap interaction**: this gate's filter changes what "the rest" means for the `+N earlier` overflow count `G-043`'s Notes already flagged as needing a cap decision — confirm whether the cap is now "N done tickets from in-progress milestones beyond what's shown" (as the mockup assumes) or something else once the real data model exists.

Blocks: none yet — no ticket exists for this; `T-158` (base board view) is unaffected and can ship without this filter/search, since the mockup's inert version (see below) treats them as visual affordances, not real data.

Notes: The companion mockup at `Docs/mockups/board/` (once finalized) includes an inert, unwired version of both asks: the Done column pre-filtered in its fixture data to only show tickets from mock "in-progress" milestones (mock "completed"/"unstarted" milestones' tickets are simply absent from Done, per Alex's rule, using fixture-only milestone status — not derived from any real endpoint), and a milestone search overlay (search input, clickable milestone list with status pills, per-milestone full task breakdown, ticket-level search hits) triggered from "+N earlier". None of it calls a real endpoint — whoever resolves this gate should decide the real data model per the Open question above, and the mockup's search-UI shape should only need to change if the resolved query shape genuinely can't support it (e.g. server-side search instead of client-side filter over a bulk fetch).

## Resolution (2026-08-22)

Decided directly with Alex (two-question round; the mockup itself — Done-column filter + milestone search overlay, both built during `G-043`'s resolution against fixture data — needed no visual change, only real wiring, same as `G-047`):

1. **Status derivation — aggregate from real ticket status, never the milestone doc's own checkboxes.** A milestone's status is computed by grouping every ticket by its `Milestone ref:` field and deriving `unstarted`/`in-progress`/`completed` from their real, live folder-based statuses (the same source `board.list` already reads). The milestone doc's `- [ ]`/`- [x]` checkbox is **never** read for this — it's a point-in-time summary a human writes, and re-deriving status from it would reintroduce exactly the staleness risk (a forgotten checkbox update silently lying) the whole board was built to avoid by reading real repo state instead of a separately maintained model. The doc's heading text is still read, but only for the milestone's display *name* — nothing else lives anywhere a ticket file can express it.
2. **Query surface — `board.list` gains `milestoneRef`; a new `board.milestones` procedure does the aggregation.** Cheap extension of the existing per-ticket parse (same `matchField` pattern every other field already uses) plus one new read-only procedure, living beside `list` in the same `board.ts` router rather than a separate `milestone.ts` file — it's tightly coupled to `board.list`'s own ticket-card fetch (reuses the same cached fetch+parse step, doesn't double the GitHub API load) and has no independent reason to be its own router.

**Search scope and the Done-column cap were already effectively decided in this gate's own filing** (see Open question above) and are confirmed here rather than re-litigated: search is a client-side substring filter over `board.milestones`' one bulk-fetched payload — no server-side search endpoint, given this is a read-only ops tool with a small milestone/ticket count. The "+N earlier" cap is exactly what the mockup assumed: the count of in-progress-milestone `done` tickets beyond what's rendered, not a different policy.

**One case the Open question didn't foresee, resolved here rather than left implicit:** a `done`-status ticket with no `Milestone ref:` field at all (predates the field, or a ticket type that never carried one) is excluded from the Done column under this filter, the same as one from a completed/unstarted milestone — it can't be attributed to an in-progress milestone, so it doesn't qualify, even though it's genuinely done work. Written directly into `T-169`'s Scope rather than left as an edge case for whoever implements it to guess at.

Ticketed as **`T-168`** (`queue/` — `board.list`'s `milestoneRef` field + the new `board.milestones` procedure, unblocked) and **`T-169`** (`backlog/` — Done-column filtering + the milestone search overlay, blocked on `T-158` and `T-168` both merging). Neither reopens or restyles `Docs/mockups/board/` — its Done-filter and search-overlay interaction was already built as an inert prototype during `G-043`'s resolution; both tickets' job is only to make it real.
