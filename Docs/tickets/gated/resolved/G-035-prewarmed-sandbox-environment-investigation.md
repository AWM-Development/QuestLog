## Resolution (2026-08-05)

Resolved interactively with Alex via `/ungate`, across a long session covering the full cost/architecture investigation this gate asked for. An earlier, separate session had drafted a different resolution on this same gate (adopting Anthropic's Managed Agents `self_hosted` environment type over Coder) and pushed it to an unmerged branch — that resolution is **superseded by this one**, not extended. It rested on an unverified product assumption (see below) that this session's own live testing disproved.

**Investigated and rejected, in order:**

1. **Anthropic Managed Agents `self_hosted` environment type** (the prior session's pick). Confirmed via its actual docs (`platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes`) that this is a *different, lower-level product* from Claude Code itself — a generic agent-building API (bash/read/write/edit/glob/grep tools, its own "skills" concept, custom tool registration), not the literal Claude Code CLI with this repo's `.claude/` config, slash commands, hooks, or subagent `Task` tool. Adopting it would have meant rebuilding `EXECUTOR_ROUTINE.md`'s entire flow against a different API, not just relocating where it runs. Rejected once the product distinction was actually verified rather than assumed.
2. **GitHub Actions self-hosted runners** (this session's first real candidate) — a genuine mechanism, spiked live end-to-end (see below), but rejected as the primary execution path once Alex reported already exceeding his GitHub Actions minutes budget from `ci.yml`'s own volume alone, with zero execution work running there. Adding long agentic ticket-execution jobs on top of an already-tight budget was the wrong direction, even with self-hosted runners keeping the *expensive* part off GitHub's meter — the orchestration model itself (one more system to run CI *and* execution through) added risk the actual finding below made moot.
3. **Fly Machines / self-hosted-worker-on-owned-hardware (Mac mini or VPS)** — priced out concretely (Fly's real per-second billing, ~$0.006-0.03/ticket at current volume) and technically sound, but abandoned once Alex raised the decisive objection: none of these paths preserve Claude Code's actual session UX (resumable sessions, `SendMessage`-style continuation, hooks/skills/subagents) — they're all "run an LLM CLI inside someone else's orchestration," which is a real, non-cosmetic downgrade from the product Alex specifically chose Claude Code for.

**The actual root-cause finding, confirmed empirically, not from docs:** Claude Code's own cloud/routines surface (`code.claude.com/docs/en/cloud-environments`) documents a real environment-caching mechanism — a setup script's filesystem snapshot is supposed to be reused across sessions, eliminating exactly the from-source pgvector/dependency-install tax `session-start.sh`'s remote branch pays every session. **This does not work on this account.** Tested live, twice, independently:
- A routine (API-fired, `/fire` endpoint) with a fresh environment and a setup script meeting every documented caching precondition (unedited between runs, network config untouched, first-ever use) produced a different random marker and a full `apt-get install` re-run on the second invocation, ~3 minutes after the first.
- An interactive `claude.ai/code` session against a separate fresh environment showed the identical result — different marker, full setup-script re-execution — one minute apart.

Both results directly contradict the docs and contradict real community reports (a dev.to writeup and GitHub issues describing the same caching mechanism working, with documented invalidation rules — none of which this session's tests triggered). The most likely explanation, based on Claude Code on the web's own docs banner (*"in research preview for Pro, Max, and Team users"* — Alex's plan is Pro) and a live, currently-open Anthropic GitHub issue describing an unrelated regression in the same caching subsystem, is a rollout/regression gap specific to this account or this moment, not anything account-targeted. Filing with Anthropic support is a separate, still-open action item — not a blocker for this decision.

**Decision:** No infrastructure migration. Given caching — the mechanism that would make the cloud surface viable — is confirmed non-functional today, and given the priority Alex placed on keeping Claude Code's actual product UX, the answer is to **stop depending on the cloud/routine surface for ticket execution** rather than build new infrastructure around a surface that isn't delivering its documented behavior:

- **Priority A — manual execution, local machine.** `EXECUTOR_ROUTINE.md`-driven ticket execution moves to interactive local sessions (Desktop app, confirmed running with `CLAUDE_CODE_REMOTE` unset) as the primary mode, replacing the nightly scheduled routine. This path was already known-cheap (native local Postgres/pgvector, no from-source build) and was live-verified clean during this same session on a real ticket (T-100): the specific database (`questlog_test_observability`) that caused two prior real incidents (T-064, T-092) migrated correctly with zero manual intervention. `T-130` (queued, P0; originally filed as `T-127`, renumbered after that number was independently claimed and shipped for a different, unrelated ticket — see `Docs/milestones/MILESTONES_V1_2_MCP.md` M-EFFICIENCY.15) hardens this path with the same verification gate T-098 already gave the remote branch, so future gaps fail loudly in seconds instead of costing a debugging session.
- **The nightly scheduled routine is paused**, not deleted — `Implementation Agent - QuestLog`'s schedule trigger stays configured but inactive until Anthropic's environment caching is confirmed working (re-test before re-enabling, don't assume a changelog entry means it's fixed) or a different infra path is deliberately chosen later.
- **Priority B — read-only/planning commands via mobile** (`/lineup`, `/morning-review`, `/ungate`) are explicitly *not* blocked by any of this — they don't provision a database or run the heavy bootstrap `EXECUTOR_ROUTINE.md` needs, so the broken caching mechanism doesn't affect them the same way. Out of scope for this gate to verify further; flag a new gate/ticket if one of them turns out to need real environment work after all.
- **Priority C — mobile-triggered implementation runs, deferred, not pursued now.** Two real candidate mechanisms exist (`Dispatch`, which runs on the paired Desktop machine using the local — working — path; `Remote Control`, which requires an already-running local session) and are worth real investigation later, but this is explicitly lower priority than getting manual/local execution solid first.
- **Revisit infra investment (self-hosted worker, Fly Machines, GitHub Actions runners) only if**: Anthropic ships working caching and it's still not enough, or actual concurrent-execution volume genuinely outgrows what local machine(s) can carry — not preemptively.
