# G-047 — Ticket-board writable move actions

Gate type: 🧠 strategy + 🎨 design

Milestone ref: M-OBS.9

Opened: 2026-08-22 — by Alex during `/ungate`'s resolution of `G-043` (ticket-board visual design). Alex asked the board mockup to support drag-and-drop between columns plus a per-card three-dot "move to column" action; both are write paths, which overturns `G-043`'s settled "read-only for v1 — no drag-and-drop, no in-board editing" constraint (carried into `T-158`'s Scope/Out-of-scope as a fixed decision, not an open question). Rather than silently expand `T-158`'s scope or quietly drop the request, `G-043` was resolved as originally scoped (read-only visual mockup, drag/three-dot UI present but non-functional/unwired) and this gate was opened to hold the "should the board actually be writable" question on its own — combined strategy + visual per Alex's explicit call, since the two are entangled here (the write mechanism shapes what the drag/move interaction can honestly promise, e.g. optimistic-update vs. confirm-then-refetch).

  - Docs/tickets/GATE_SPEC.md, Docs/tickets/TICKET_SPEC.md (`Blocked on:`/`Gated on:` semantics — a board move has to either respect these or the gate must decide it's out of the move UI's power to override them, e.g. can't drag a `Gated on:`-carrying card out of Gated)

Open question: Should the `/board` route become writable, and if so, how?
  - **Mechanism**: what actually moves a ticket — a real filesystem/git mutation (moving the `T-###.md` file between `Docs/tickets/` folders, committing, pushing — mirroring what `/promote`/the executor do today) via a new authenticated write endpoint? Or does "move" only ever stage an *intent* (e.g. open a PR, or post a comment/flag) that a human or the executor still finalizes?
  - **Guardrails**: which columns can a card be dragged into/out of at all — e.g. is dragging a card with an open `Gated on:` chip out of Gated blocked outright (since only `/ungate` may clear that), and does In-progress/Done stay drag-target-only for the executor, never Alex?
  - **Auth/safety**: this is a GitHub-API-backed static ops tool (`apps/observability-dashboard`, T-057) — what does a write path need that the read-only `board.list` endpoint doesn't (auth, rate limits, conflict handling if the executor mutates the same ticket mid-drag)?
  - **Visual**: given the mechanism decided above, does the interaction stay optimistic-drag-then-confirm, or does a move always require the three-dot menu's explicit "Move to <column>" action with a confirm step (no bare drag-drop) — and what does the three-dot menu's full action list look like beyond "move" (open ticket file, open PR if in-progress, etc.)?

Blocks: none yet — no ticket exists for a writable board; `T-158` stays read-only and unaffected by this gate's resolution.

## Resolution (2026-08-22)

Decided directly with Alex (three-question round, not a mockup — the "🎨" half of this gate turned out to already be satisfied by `G-043`'s mockup, since the drag/⋮-menu interaction it prototyped needed no visual change, only real wiring):

1. **Mechanism — real git mutation via a new authenticated write endpoint.** `board.move` moves the ticket's `.md` file between `Docs/tickets/` folders and commits directly to `develop` — no PR/staged-intent indirection. Mirrors what `/promote`/the executor already do to repo state today, just triggered from the board instead of Claude Code.
2. **Guardrails — only the human-owned columns are movable.** A card can move between `Backlog`↔`Queue`↔`Blocked` only. `Gated` stays locked outright (only `/ungate` may clear a `Gated on:` line — the write endpoint refuses even if asked). `In-progress`/`Done` are never a drag source or target from the board — those reflect real branch/PR/executor state that dragging a card can't actually make true, so allowing it would just let the board lie about reality. This is a narrower guardrail than "any column except Gated" (the alternative considered) specifically to avoid the board ever creating a desync between what it displays and what's actually running.
3. **Confirm — lightweight inline confirm, not a full MCP-style preview/confirm/audit round trip.** `.claude/rules/mcp.md`'s preview/confirm/audit pattern exists because an MCP tool call can originate from an LLM agent that might misfire — the safety net is the point. A board drag/drop or ⋮ pick already originates from Alex's own direct click; the click *is* the human-in-the-loop step that pattern exists to guarantee. What it's missing is protection against a **fumbled** click (wrong column, mis-drop) — solved cheaply with an inline "Move T-158 → Queue?" confirm before the write fires, not a second network round trip. The write's own git commit is the audit trail (who/what/when, same as every other repo mutation in this pipeline) — no separate `write_requests`-style ledger needed for this surface.

**Auth stance, decided during ticket drafting (not asked as a fourth question — no existing auth mechanism exists yet to weigh alternatives against):** the write endpoint inherits whatever trust boundary `apps/observability-dashboard` already has (currently none beyond network reachability — it's an unreleased internal tool). This is flagged explicitly in `T-166`, not silently assumed: a write-capable endpoint is a materially higher-risk surface than `board.list`'s read, and this decision should be revisited the moment this app becomes reachable somewhere less trusted than today.

**New pattern, worth naming plainly:** every existing GitHub-API caller in this codebase (`board.list`, `T-055`'s diff-stat sync) is read-only. `T-166` is this codebase's first server-initiated git write — a running server process holding credentials that can push to `develop`. Sized `L` (not `M`) specifically because it's a genuinely unfamiliar pattern here, not an extension of an established one, per `TICKET_SPEC.md`'s tier rubric.

Ticketed as **`T-166`** (`queue/` — the write endpoint, unblocked) and **`T-167`** (`backlog/` — wiring the mockup's existing drag/⋮-menu interaction to it, blocked on `T-158` and `T-166` both merging). Neither reopens or restyles `Docs/mockups/board/` — its interaction was already built as an inert prototype during `G-043`'s resolution; `T-167`'s job is only to make it real.
