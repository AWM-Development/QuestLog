# Executor Routine

**Location:** `Docs/tickets/EXECUTOR_ROUTINE.md`
**Last Updated:** 2026-08-06
**Purpose:** The procedure the nightly scheduled agent follows. Kept here, version-controlled, so changes to the nightly loop are diffable and reviewable like everything else in the pipeline.

**How the scheduler reaches this file (updated 2026-07-30):** the scheduled agent's prompt is *not* a copy of this document. The prompt is two lines, the same shape as `.claude/commands/executor.md`:

```
git fetch origin develop && git show origin/develop:Docs/tickets/EXECUTOR_ROUTINE.md
Read that output in full and follow it exactly, starting at Step 1.
```

So this file is read fresh from the checkout on every run: **editing it here is sufficient, and takes effect on the next nightly run once merged to `develop`.** There is no separate copy to keep in sync, and no manual scheduler update after a routine change.

The one exception is that first line, which is duplicated into the scheduler prompt itself and therefore *cannot* be changed by editing this file — the same bootstrap also appears in `.claude/commands/executor.md` and `.claude/commands/promote-execute.md`, which can. A change to the bootstrap specifically needs a one-time manual edit of the scheduler prompt by Alex; a change to anything else in this routine does not. (T-069 removed the prior `git checkout -B develop origin/develop` from this line — a concurrent session sharing the same sandbox no longer gets its working tree yanked out from under it, since each session now works in its own git worktree per Step 0/2 below.

**Fixed 2026-07-30 (found live, during T-037's own run):** the two-line form above — `git fetch origin develop` followed by a separate, plain `Read Docs/tickets/EXECUTOR_ROUTINE.md` — let an agent read this file *before* the fetch's effects were visible to it. `git fetch` only updates the `origin/develop` remote-tracking ref; it never touches the working tree, and per Step 0 below the working tree is explicitly not trustworthy ("may be created from an arbitrary starting point"). A session that (harmlessly, from its own point of view) issued the fetch and the read as two independent actions instead of one strictly-ordered one ended up reading whatever stale copy of this file was already sitting in its working tree — in the observed case, a pre-T-069 version with no worktree isolation and no usage-capture step — and executed an entire ticket against it, skipping both. The fix: chain the fetch and the read into one command, `git show origin/develop:<path>` instead of a raw file `Read`, so the content returned is pinned to the just-fetched ref regardless of working-tree state — the identical technique Step 1 already uses to read ticket files safely. Alex applied this exact edit to the live scheduler prompt directly, in the same session this was found, rather than waiting on a merge.)
**Assumes:** `Docs/tickets/TICKET_SPEC.md` (ticket format), `Docs/tickets/GATE_SPEC.md` (gate-stub format, `Gated on:` field), `Docs/tickets/BLOCKED_TEMPLATE.md` / `REPORT_TEMPLATE.md` (protocols), `.claude/agents/reviewer.md` (review step), `.claude/skills/tdd-loop/SKILL.md` (implementation loop), and the branch model documented in `Docs/IMPLEMENTATION_NOTES.md` (`main` deployed, `develop` integration).

## Runners

This routine is designed to be runner-agnostic — a fetch-then-`git show`
bootstrap plus prose any agent that can run `git`/`gh` can execute
(confirmed live, `Docs/tickets/gated/resolved/G-020-pipeline-audit-and-improvement.md`
Notes §1: `/lineup`'s procedure ran correctly end-to-end under a
non-Claude agent, including Step 1's dedup classification). Two points in
this routine assume Claude Code specifically:

- The CRITICAL BRANCH RULES block's `Model: sonnet, always` line. A
  different runner should follow whatever runner/model its own ticket
  names instead, once `TICKET_SPEC.md`'s `Runner:` field lands (`T-107`)
  — until then, this line only binds a Claude Code run.
- Step 7's `capture-usage` invocation (and Step 6's equivalent for a
  blocked run). This is Claude-Code-only — it resolves cost from
  `CLAUDE_CODE_SESSION_ID` plus a `~/.claude/projects/**/<session>.jsonl`
  transcript, and no other runner exposes an equivalent (`G-020` Notes
  §3). A different runner should skip this step entirely, until a
  runner-neutral cost adapter exists (`T-109`).

Every other step — Step 0's fetch-only bootstrap, Step 1's ticket
selection and dedup classification, Step 3's context loading, Step 4's
TDD loop, Step 5's review, Step 6's blocked protocol, and the rest of
Step 7 — is already runner-neutral, per `G-020` Notes §1.

You are the QuestLog nightly ticket executor.

CRITICAL BRANCH RULES — NEVER VIOLATE:
- `main` is the deployed branch. NEVER push to it, NEVER target it, NEVER base a ticket branch on it. If any step would require touching `main`, STOP and log it as a blocker.
- Ticket branches are cut from `develop` and PR'd back into `develop`. `develop` → `main` is a separate release step only Alex performs.
- NEVER merge any branch — not into `develop`, not into `main`. You open a PR against `develop`; you never merge it.
- The only ref you ever push is the current ticket's feature branch — its nominal `Branch:` name, or your session's harness-assigned branch as Step 2's fallback (or, when resuming per Step 1 case 4, the branch that ticket's prior work actually lives on). Never push `develop`, `main`, or any other existing branch: the git proxy blocks those pushes mechanically, and you must never attempt them regardless.
- Model: sonnet, always. Never opus/fable for execution.

## Known sandbox constraint: no real Docker builds
This sandbox cannot pull images from Docker Hub (blob-layer CDN returns `403 Forbidden` — confirmed repeatedly across T-023/T-024/T-042, see `Docs/IMPLEMENTATION_NOTES.md`). If a ticket's exit condition calls for `docker build`/`docker pull`, do not attempt it — go straight to the established substitute: run the bundled `dist/*.js` output directly under plain `node`, and manually simulate any Dockerfile `COPY` step whose behavior needs confirming. State in the report that the substitute was used and why (citing this note), rather than re-discovering and re-documenting the same restriction from scratch. A real `docker build` outside this sandbox is still the correct final check before an actual deploy — that's `Docs/DEPLOY_SETUP_CHECKLIST.md`'s job, not this routine's.

## Step 0: Fetch only — never check out in the shared primary working directory
The sandbox this routine runs in may be created from an arbitrary starting point (not necessarily `develop`), and unlike a single-tenant remote sandbox, the primary working directory of a locally-run `/executor` or `/promote-execute` may be shared with another concurrent session (`Docs/IMPLEMENTATION_NOTES.md` § T-069). Never check out any branch here. Before anything else, unconditionally:
```bash
git fetch origin develop
```
That's it — do not `git checkout` anything in this directory. Step 1 reads every ticket file it needs straight off `origin/develop` (`git show origin/develop:<path>`), never touching a working tree. Step 2 creates or enters this session's own git worktree at `tmp/worktrees/T-###/`, branched from `origin/develop`, and every step from there on runs inside that worktree — never back in the primary directory. See `Docs/IMPLEMENTATION_NOTES.md` § T-069 for the full convention (path layout, why `tmp/worktrees/` and not `.claude/worktrees/`, creation/entry commands) — this section only covers what changes step-by-step.

**Provisioning fallback:** a scheduled/`remote_trigger` launch can reach this point without its `SessionStart` hook having fired at all (confirmed live — no `pnpm install`/provisioning output anywhere before the first turn), not merely a stale copy of it. No edit to `session-start.sh` fixes that, since the event invoking it never dispatched. Check before proceeding: if `node_modules/` is missing, or (`CLAUDE_CODE_REMOTE=true`) `pg_isready -h localhost -p 5433 -q` fails, run `bash .claude/hooks/session-start.sh` directly. Harmless if `SessionStart` already ran — same idempotent checks either way.

**STALENESS_THRESHOLD_HOURS = 6** — the age past which a claimed-but-unfinished branch (Step 1 case 4) is treated as abandoned rather than actively owned. Defined once here; Step 1 and `.claude/commands/promote-execute.md` both reference this value rather than hardcoding their own copy. Too low steals a slow ticket out from under a session still working it; too high leaves a genuinely crashed run stranded for most of a day before anything picks it back up. 6 hours is longer than any observed real ticket run and short enough that a crash doesn't strand work overnight.

## Step 1: Pre-flight (cheapest possible check — do this before reading anything else)
This entire step is read-only against `origin/develop` and `origin`'s refs — nothing here touches a working tree, so it's safe to run from the shared primary directory before any worktree exists (the ticket id a worktree would be named for isn't known until this step finishes). The one exception is the reap sweep immediately below, which only ever *removes* a worktree that's already provably done with — it never touches the primary working tree's own files, and only acts on worktrees whose branch it has independently confirmed is merged, so it's still safe to run unconditionally from the shared primary directory before any candidate ticket is known.

**Worktree reap sweep (T-087):** before selecting a ticket, sweep `tmp/worktrees/*` for entries that are safe to tear down. For each entry: resolve its checked-out branch (`git -C tmp/worktrees/<name> rev-parse --abbrev-ref HEAD`), then confirm via GitHub CLI that its PR actually merged — `gh pr view <branch> --json state,mergedAt` (or `gh pr list --search "<branch> in:head" --state all --json state,mergedAt` if `gh pr view` can't resolve the branch directly). A ticket file present in `Docs/tickets/done/` is not by itself sufficient confirmation — `done/` also covers won't-fix tickets whose branch may never have opened a PR at all, so always check the branch's own PR state, not the ticket file's location. If the PR state is `MERGED`, reap it: `scripts/reap-worktree.sh <name>` (never pass `--force` from this automated sweep — an entry the script itself refuses due to uncommitted changes is a signal something is wrong with a supposedly-merged branch, not something to force through unattended; note it, e.g. `worktree <name> skipped by reap sweep — script refused (uncommitted changes) despite merged PR`, and move on). If the PR is still open, not found, or the branch can't be resolved, leave the entry untouched and move on to the next. This sweep never touches `develop`'s ticket directories and has no bearing on ticket selection below — it's cleanup, not part of the candidate-list logic.

First, identify unblocked backlog tickets to promote — but don't write anything yet: list `Docs/tickets/backlog/*.md` (`git show origin/develop:Docs/tickets/backlog/` or an equivalent read against the remote). For each one:
- If it has a `Gated on: G-###` line, **never promote it, regardless of its `Blocked on:` state.** That field only clears via `/ungate` (`.claude/skills/ungate/SKILL.md`, `Docs/tickets/GATE_SPEC.md`) — the executor never touches it. As a cheap sanity check, confirm `Docs/tickets/gated/G-###-*.md` still exists on `origin/develop`: if it doesn't (the gate was resolved and moved to `gated/resolved/` but this ticket's line was never cleared — a sync bug, not a green light), note it (`T-### flagged — Gated on: G-### not found in gated/, may be stale`) and leave the ticket untouched. Move on to the next candidate either way.
- Otherwise, read its `Blocked on:` line and check whether every ticket id it names has a matching file under `Docs/tickets/done/` on `origin/develop` (a match means that ticket's PR has merged, since a ticket file only lands in `done/` once its own PR merges). If every named id is cleared, mark it a promotion candidate — record its id, but don't `git mv`/commit anything yet; that write happens in Step 2, once this session's worktree exists. If any named id isn't yet in `done/`, leave that ticket alone and move on to the next one — do not stop at the first still-blocked ticket.

`backlog/` tickets are never picked up for execution directly, only ever promoted to `queue/` first.

Then build the candidate list: `Docs/tickets/in-progress/*.md`, then `Docs/tickets/queue/*.md` (both read off `origin/develop`) sorted by each ticket's `Priority:` field (`P0` before `P1` before `P2`; treat a missing field as `P1`), with numeric `T-###` id as the tiebreak within a tier (including anything just marked for promotion above). This is a selection-order sort only, not a filter — every queued ticket still gets picked up eventually, just not necessarily oldest-first anymore. Priority never overrides `Blocked on:`/`Gated on:`: those still gate a ticket out of the candidate list entirely, same as before, before tier sorting is even considered. If both directories are empty: output `NO_TICKET_QUEUED. Exiting.` and stop. Do not read AGENTS.md, rules, or any other file.

`develop`'s copy of these directories can lag reality (`Docs/tickets/TICKET_SPEC.md` §"Why develop's ticket directories can lag reality") — a ticket sitting in `queue/` may already be shipped-and-under-review, previously blocked, or *actively claimed by a session working it right now* (T-069 made the claim real — see case 4 below), not untouched.

**Ledger-first, narrow-fallback resolution (T-116).** Read `Docs/tickets/.merge-ledger.json` off `origin/develop` once (`git show origin/develop:Docs/tickets/.merge-ledger.json` — treat a missing file as `[]`, since the ledger starts empty and only ever gains entries going forward). `.github/workflows/ticket-status-ledger.yml` upserts an entry (`{ ticketId, prNumber, branch, mergedAt }`) into this file the moment a `(feat|chore|fix|refactor)/<group>/t-###-<slug>` branch merges into `develop` — see `Docs/IMPLEMENTATION_NOTES.md` § T-116 for the file's format and the Action's trigger design. A candidate whose ticket id already has a ledger entry is already merged; note it (`T-### skipped — ledger shows merged (PR #<n>, <mergedAt>)`) and continue to the next candidate with no further check. In practice this rarely fires — a ticket's own PR merge already moves its file out of `queue/`/`in-progress/` via Step 7's own commit, so a merged ticket is rarely still a candidate at all — but it's a real, free defensive check against the sync-lag cases this section already documents, so always do it before anything live. **The ledger recognizes any of `feat|chore|fix|refactor` as the implementation-branch prefix** (widened from `feat/`-only — found live, five real merged tickets under `chore/`/`fix/` had silently gotten no ledger entry: `Docs/IMPLEMENTATION_NOTES.md` § T-116's amendment). Still deliberately narrow, not "anything containing `/t-###-`": that broader match would also catch pre-2026-07-16 `tickets/t-041-...`-style ticket-*creation* branches (docs-only filing PRs), poisoning the "already merged" signal. Any candidate whose actual `Branch:` prefix isn't one of those four still falls through to the live check below, same as any other candidate the ledger doesn't resolve.

For every candidate the ledger doesn't resolve, replace the old full-repo scan with a **narrow, per-candidate live check** scoped to that one candidate's nominal `Branch:` field — cheap because it only ever runs for the handful of candidates actually reached before a pick, never the whole repo's PR history:
- A head-filtered PR query: `gh pr list --head <branch> --state all --json number,title,state,mergedAt,headRefName` if `gh` CLI is available, otherwise the equivalent GitHub MCP/connector list-endpoint tool (`list_pull_requests` — **not** a search-endpoint tool, which reintroduces the 5-operator/422 risk a full scan was already avoiding) with `head: "<owner>:<branch>"`, `state: all` (confirmed live: this returns only PRs whose actual head branch is the one queried — e.g. querying `feat/m-pipeline/t-110-ci-gate-guard` returns exactly PR #179 and nothing else, querying an untouched branch returns `[]`). Because the query itself filters by head branch, **a result can never be a title-matching false positive** — the 8-of-20 filing-PR false-positive case older versions of this section warned about (a ticket-writer/`ungate` filing PR listing every newly-drafted ticket id in its own title, despite running on the filing session's own branch) is structurally impossible here, not just avoided by convention. **Determine merge status from whether `merged_at`/`mergedAt` is present on a returned PR, not from a `merged` boolean field** — still unreliable in a REST listing context (verified in practice: a GitHub MCP list tool returned `merged: false` on two PRs independently confirmed merged via a single-PR read; `merged_at`'s presence/absence was correct on the same PRs). This is unrelated to the ledger Action's own `pull_request.merged` webhook field, which *is* trustworthy — that field is synchronous with the merge event itself, a fundamentally different context from a REST listing computing `merged` after the fact; don't let this narrow check's distrust of the listing-endpoint field bleed into distrust of the Action's webhook field, or vice versa.
- If the head-filtered query returns nothing, check whether the branch itself exists at all: `git ls-remote --heads origin <branch>` (a single ref name, not the full listing).

Classify each candidate against its own narrow check, in priority order, stopping at the first pick or resume:

1. **No matching PR and no matching branch** — this ticket has never been touched. Pick it and proceed to Step 2. Stop the loop here.
2. **Matching PR found, open** — already shipped, awaiting Alex's review, on whatever branch it actually landed on. Do not check it out, do not touch it, do not push to it. Note it (`T-### skipped — PR open on <actual branch>`) and continue to the next candidate.
3. **Matching PR found and closed without merge, or a matching branch with no PR, and `Docs/tickets/blocked/T-###-slug.md` exists** — already hit its iteration cap and is waiting on Alex to unblock it (`TICKET_SPEC.md` §"Unblocking a blocked ticket" — you never do this yourself). For the "matching branch with no PR" sub-case, the branch exists by definition, so check it directly: `git show <branch>:Docs/tickets/blocked/T-###-slug.md`. For the "matching PR, closed without merge" sub-case, **do not assume the head branch still exists** — GitHub deletes a PR's source branch by default once the PR closes, confirmed live (a genuinely-closed-without-merge candidate's branch was already gone, `git show <branch>:...` failed with `fatal: invalid object name`). Instead fetch the PR's permanent ref, which GitHub retains for the life of the PR regardless of branch deletion: `git fetch origin refs/pull/<number>/head && git show FETCH_HEAD:Docs/tickets/blocked/T-###-slug.md`. Note it (`T-### skipped — blocked`) and continue to the next candidate.
4. **Matching branch found, no PR, not blocked** — either a prior run was interrupted before this ticket reached `done/`/`blocked/`, or (since T-069) another session has this ticket claimed right now and just hasn't pushed the final commits yet — Step 2 pushes the branch at pickup, so a matching branch alone no longer implies an interrupted run. Disambiguate with a staleness check: `git log -1 --format=%cI origin/<branch>` gives that branch's most recent commit timestamp. If it's younger than **STALENESS_THRESHOLD_HOURS = 6** (defined in Step 0), treat the ticket as actively owned — note it (`T-### skipped — branch claimed <age> ago, within staleness window`) and continue to the next candidate, same as cases 2/3. If it's older than the threshold, treat it as an abandoned/crashed run and resume: this session's worktree doesn't exist yet, so create it now by entering the existing branch rather than cutting a new one — `git worktree add tmp/worktrees/T-###/ <actual-branch-name>` (fetch it first if needed), `cd` into it, `git pull`. **Bootstrap this worktree's own environment now, same as Step 2's fresh-pickup path (T-127):** `CLAUDE_PROJECT_DIR="$(pwd)" bash .claude/hooks/session-start.sh` — this worktree is just as new as one Step 2 would have created, and hits the identical missing-`node_modules`/missing-Postgres-stack condition. Write the ticket id to `tmp/.active-ticket` inside that worktree (same as Step 2 does for a fresh pickup — a resumed session is just as actively working the ticket, and the marker doesn't survive across sessions or worktrees). Proceed to Step 3 from wherever the branch's commit history shows it left off. Stop the loop here.

**Not actually preserved by either the old or new version of this section — flagged here rather than silently carried forward as if it were:** a ticket whose Step 2 push under its nominal `Branch:` name gets rejected falls back to the session's harness-assigned `claude/*` branch instead (CRITICAL BRANCH RULES above, and Step 2 below — a live, standing fallback, not a pre-2026-07-16 relic). Once that happens, this ticket's PR/branch no longer matches its nominal `Branch:` field at all, and **no version of Step 1 — before or after this rewrite — has ever had a way to find it again**: the pre-T-116 text's own matching-PR/matching-branch rules explicitly scoped the `claude/*` accommodation to "runs before 2026-07-16" only (`Docs/tickets/EXECUTOR_ROUTINE.md`'s git history), and even the pre-T-116 full `git ls-remote --heads origin` listing only matched a candidate whose nominal `Branch:` field appeared as a *substring* of a returned ref name — which a harness-assigned `claude/*-<random>` name never does. This rewrite's narrow per-candidate check inherits the exact same blind spot, not a new one it introduces. Left as a known, pre-existing gap outside this ticket's scope (T-116 replaces *how* the two already-documented matching mechanisms get their answers, not what they're scoped to match against) — worth its own follow-up ticket if it's ever actually hit in practice, rather than fixed as a drive-by here.

If the loop exhausts every candidate without a pick (case 1) or a resume (case 4): output `NO_ACTIONABLE_TICKET — every queued ticket is already shipped (PR open), blocked, or actively claimed. Exiting.` and stop. Do not start work on a skipped ticket's branch under any circumstance, even if it's the only thing in `queue/`.

**Pre-flight guard check (T-115), resolving `G-020` Q2's "does the same logic also run as a pre-flight" question — yes.** Once a candidate is chosen above (a fresh case-1 pick or a case-4 resume), before this session commits any further effort (Step 3's context load and Step 4's implementation), invoke the same enforcement scripts CI runs on the eventual PR — `scripts/ci-gate-guard.sh`, `scripts/ci-scope-guard.sh`, `scripts/ci-report-guard.sh`, `scripts/ci-exit-condition-guard.sh` (`T-110`/`T-111`/`T-112`/`T-113`'s own scripts, called as-is — this never reimplements their logic) — against that candidate. The mechanics run inside Step 2 below, right after that step's pickup commit, since only then does a real `origin/develop...HEAD` diff exist for these scripts to check:
- `scripts/ci-gate-guard.sh` re-checks the picked ticket's own `Gated on:`/`Blocked on:` state via the exact same logic CI enforces on a PR — catching drift between this section's hand classification above and the authoritative check, not duplicating it. A candidate that fails this (its ticket file still carries either field unresolved — a sync bug, since the classification above should already have excluded it) is treated exactly like a case 2/3/4 skip: note `T-### skipped — gate-guard failed at pre-flight: <message>`, abandon the worktree without pushing, and return to this candidate loop for the next one.
- `scripts/ci-scope-guard.sh`, `scripts/ci-report-guard.sh`, and `scripts/ci-exit-condition-guard.sh` are invoked identically, against the same diff. For a fresh case-1 pick, that diff is only the pickup commit itself (no report exists yet, no out-of-scope files touched), so all three pass trivially — they're wired in regardless so a case-4 resume, whose branch may already carry an interrupted prior session's work, gets re-verified against every check before this session continues it rather than only the gate-guard one. A failure on a resume is treated the same as a fresh-pick gate-guard failure above: note it, abandon, move on.
- The red-check (`T-114`, `scripts/ci-red-check-guard.sh`) is deliberately **not** part of this pre-flight — it needs a completed implementation diff to run the new tests against `develop`'s prior code, which doesn't exist until Step 4 finishes. It stays a PR-time-only check.
- Any non-zero exit here is a failed pre-flight for this candidate, full stop — this session doesn't attempt to fix the underlying issue itself (that's either a `/ungate`/promotion action outside this routine, for gate-guard, or a sign the candidate's own branch needs Alex's attention, for a scope/report/exit-condition failure on a resume).

## Step 2: Enter your worktree and claim the ticket (new tickets only — skip if resuming per Step 1 case 4, which already did this)
- Create this session's worktree from the primary directory, branched from `origin/develop` fetched in Step 0, using the exact name in the ticket's `Branch:` field: `git worktree add tmp/worktrees/T-###/ -b <branch-name> origin/develop`. Then `cd tmp/worktrees/T-###/` — every remaining step in this routine runs from inside this worktree, not the primary directory. `git worktree add` doesn't touch or require any particular branch to be checked out in the primary directory, which is why Step 0 no longer checks one out. (See `Docs/IMPLEMENTATION_NOTES.md` § T-069 for the convention this follows and why `tmp/worktrees/`, not `.claude/worktrees/`.)
- **Bootstrap this worktree's own environment now, before anything else in this step (T-127):** `CLAUDE_PROJECT_DIR="$(pwd)" bash .claude/hooks/session-start.sh` — a fresh worktree has no `node_modules` and no per-worktree Postgres stack of its own (`T-072`'s per-worktree isolation), and the session's own `SessionStart` hook only ran against the *primary* directory, before this worktree existed. Same invocation form Step 6/7 already use for `capture-usage`. Idempotent — a safe no-op if this worktree was already bootstrapped (e.g. resuming later in the same long-running session), same property Step 0's remote-provisioning fallback already relies on.
- Now, inside the worktree, commit any backlog promotions Step 1 identified but deferred: for each, `git mv` the file from `Docs/tickets/backlog/` to `Docs/tickets/queue/`, delete its `Blocked on:` line, commit (`chore: promote T-### from backlog — <blocking ticket(s)> merged`).
- `git mv` the ticket from `Docs/tickets/queue/T-###-slug.md` to `Docs/tickets/in-progress/T-###-slug.md`, commit (`chore: pick up T-### — move to in-progress`).
- **Run the pre-flight guard check now (T-115), before reading the ticket or pushing anything:** `scripts/ci-gate-guard.sh`, then `scripts/ci-scope-guard.sh origin/develop <branch-name> develop`, then `scripts/ci-report-guard.sh origin/develop <branch-name>`, then `scripts/ci-exit-condition-guard.sh origin/develop <branch-name>` (all four, `origin/develop` as base ref, this worktree's own `<branch-name>` as head — see Step 1's "Pre-flight guard check" note above for what each one catches and why the other three trivially pass on a fresh pick). If any exits non-zero: do not proceed — `cd` back to the primary directory, `git worktree remove tmp/worktrees/T-###/ --force` (nothing has been pushed yet, so there's nothing on `origin` to clean up), note the failure per Step 1's language above, and return to Step 1 to pick the next candidate instead of this one. All four green: continue below.
- Read the ticket in full. Note its Branch field, Context files list, Mockup field, Scope, Out of scope, Exit condition, and Iteration cap.
- Write the ticket id to `tmp/.active-ticket` (plain text, e.g. `T-###`, written inside this worktree — resolves separately per worktree since each is its own directory tree) — this is the explicit signal `capture-usage` reads to attribute this session's usage correctly (`packages/core/src/usage-capture/capture-usage.ts`'s `resolveActiveTicketId`; see Docs/IMPLEMENTATION_NOTES.md § T-046 and `G-011`'s resolution).
- **Push the branch now** — `git push -u origin <branch-name>` — carrying the pickup commit(s) above. This is the ticket claim (T-069): it turns Step 1's `git ls-remote`/`gh pr list` dedup check into a real mutex instead of a check-then-act race two sessions could both pass, at the cost of a second push to this same branch later (Step 6/7's wrap-up push) — CRITICAL BRANCH RULES still permits this, since it's still only ever this ticket's own feature branch. The git proxy permits creating a new branch name even though it isn't your session's assigned `claude/*` branch (verified empirically in this repo — T-004's session, 2026-07-15). If this push is rejected (e.g. proxy behavior has tightened): push the same commits to your session's harness-assigned branch instead — same one-ticket/one-branch/one-PR shape, different name — and flag the deviation under "Anything Alex must decide" in the eventual report. Either way, Step 1's dedup check on future runs is unaffected, since it searches by ticket id, not by exact branch name.

## Step 3: Load context — ONLY what the ticket names
**`XS`-tier tickets (T-102):** read only `AGENTS.md` and the ticket file itself — no `Context files:` reads at all. An `XS` ticket's body already inlines the exact before-text and precedent snippet needed to locate and make the edit (`TICKET_SPEC.md`'s `Complexity tier` field notes), so there's nothing else to load. Skip straight to Step 4's `XS` branch.

**`D`-tier tickets (T-134): unchanged from the default below — no separate branch.** A docs-only sweep often needs to read several existing docs to know current wording before editing them, unlike `XS`, whose ticket body fully inlines the before-text and precedent snippet so there's nothing left to read. `D` gets its process-weight cut in Steps 4 and 5, not here.

**Every other tier:**
- Read `AGENTS.md` (always — it's the canonical constitution, ~40 lines; `CLAUDE.md` itself is just a thin pointer to it, per T-105) together with every file listed in the ticket's `Context files:` field, as parallel tool calls within a single assistant turn — the full list is known upfront, so there's no reason to spread these reads sequentially across multiple turns, each re-sending the growing conversation. Read nothing else, unless you discover mid-ticket that something is missing — if so, note that as a scoping gap in the eventual report rather than silently pulling in extra files. (This batching applies only to this upfront context-loading step — Step 4's TDD loop necessarily reads/writes files sequentially as work proceeds.)
- `.claude/rules/*.md` load automatically by path glob as you touch matching files — you don't need to seek them out manually.
- If `Mockup:` names a path, read it (read-only — never edit anything under `Docs/mockups/`). If it's `none`, there's no visual component.
- If the ticket has an unresolved 🧠 strategy gate anywhere in its scope, STOP on that specific item and continue with whatever in the ticket doesn't depend on it. Don't just log it in the eventual report — file it as a gate-stub now: check whether `Docs/tickets/gated/*.md` already has one for this exact question (filed during ticket-writing); if not, create `Docs/tickets/gated/G-###-slug.md` per `Docs/tickets/GATE_SPEC.md` (next unused `G-###`), naming this ticket's id and branch in `Blocks:`/`Notes:`, and commit it (`chore: file G-### — gate surfaced during T-###`). This is what makes the gap visible to `/ungate` instead of only living inside this ticket's morning report. A 🎨/mockup reference is never a gate — proceed.

## Step 4: Implement — TDD, per `.claude/skills/tdd-loop/SKILL.md` (weight gated by Complexity tier, T-084)
Process weight below is gated on the ticket's `Complexity tier` field (`TICKET_SPEC.md`), not applied uniformly — a docs-only edit has no meaningful failing test to write, and forcing the full ceremony on one burns turns proportional to fixed process, not diff size (T-070: a 4-file, 7-line docs-only ticket cost ~$3.87 across 136 turns).

**`XS`-tier tickets (T-102), checked first, ahead of the `S`-docs-only branch below:** no per-checkpoint Red/Green/Refactor iteration. Write the one (or two, matching the ticket's Exit condition) test(s) and the fix together, in a single pass, using the before-text and precedent snippet the ticket already inlined in Step 3. Then run `scripts/run-tests-quiet.sh` once — still an unconditional gate, must be green before proceeding, same bar every other tier enforces, just without the iterate-per-checkpoint ceremony. Commit with message `feat(T-###): <short description>` once green. Skip straight to Step 5's `XS` branch.

**S-tier tickets whose Scope touches no application code** (docs/config-only — confirmed by the ticket's own Scope naming only `.md`/config files, never inferred from the diff after the fact once work is underway): skip the Red/Green/Refactor requirement below entirely — there's no meaningful failing test for a markdown/config edit. Make the documented change directly, then run `scripts/run-tests-quiet.sh` once as a single end-of-work verification pass (still the exact same lint/typecheck/test regression gate every tier requires — this collapses the per-checkpoint iteration, not the gate itself) instead of looping it per checkpoint in Scope. Commit with message `feat(T-###): <short description>` once green.

**`D`-tier tickets (T-134): no branch of their own — reuse the `S`-docs-only branch above.** A `D` ticket is by definition all-`.md` Scope (`TICKET_SPEC.md`'s field notes), so it already qualifies for the docs/config-only path immediately above: single end-of-work `scripts/run-tests-quiet.sh` pass, no per-checkpoint Red/Green/Refactor. `D` only changes Step 5, not this step.

**M/L-tier tickets, and any S-tier ticket that touches application code**: unchanged — full TDD loop, per checkpoint in the ticket's Scope:
1. Red: write a failing test for the behavior. Confirm it fails for the right reason.
2. Green: minimum code to pass.
3. Refactor with tests green.
4. Run `scripts/run-tests-quiet.sh` (same fail-fast lint → typecheck → test chain, but only prints per-stage summaries on success — full output for a failing stage only; logs persist under `tmp/test-logs/` for Step 7's pasted evidence).
5. If a single blocking failure survives 3 distinct attempted approaches (the ticket's Iteration cap — check the ticket for a different number), STOP. Do not attempt a 4th. Go to Step 6 (Blocked).
6. Commit with message `feat(T-###): <short description>` once green.

Step 5's reviewer subagent still runs for every tier except `XS` and `D` regardless of which path above applied — this only changes the implementation-loop overhead leading up to review, never review coverage itself.
