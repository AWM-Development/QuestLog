#### ⚠️ Caveat on 2.1/2.2 — the import pipeline is not triggered by upload (the "broken SourcesPage")

The upload endpoint (`server.ts` `POST /api/campaigns/:campaignId/sources/upload`) creates the source row and stores the file — **and stops**. `importService.processPendingSources` runs only in two places:

1. An `onReady` hook — **server startup only** (`server.ts:262`)
2. The manual worker script `pnpm run process-imports`

So a file uploaded while the server is running sits at `pending` forever; the SourcesPage ImportQueue polls and never sees progress until the server restarts. **The dev DB corroborates this: it contains exactly one source (`Denver DnD Notes.pdf`, uploaded 2026-04-27) stuck at `pending`, with 0 chunks and 0 embeddings.** Un-breaking this = trigger processing after upload (fire-and-forget call or interval poller). This is the concrete "un-break SourcesPage" work the pivot calls for.

#### 🔍 Deep-dive: Task 2.3 — vector similarity search

Question asked: does the search service exist, is it wired to a tRPC endpoint, and has it ever demonstrably returned relevant chunks end-to-end?

- **Service exists and is sound.** `search.service.ts`: embeds query via Voyage (`input_type: "query"`), pgvector cosine distance (`<=>`), campaign-filtered, top-k, joins source names. Config matches schema (1024-dim).
- **tRPC endpoint exists.** `search.searchSources` in `routers/search.ts` with Zod validation (`SearchSourcesInput`). No frontend caller — debug-only, as the milestone intended.
- **End-to-end has NEVER been demonstrated.** Three independent lines of evidence:
  1. `search.service.test.ts` uses **synthetic basis-vector embeddings and a mocked Voyage fetch** — it proves the SQL ordering/filtering, not real retrieval quality. The milestone's own test spec said "integration test with real embeddings in test DB"; that was not done.
  2. `search.integration.test.ts` **mocks the search service entirely** — it proves router wiring only.
  3. The dev database has **0 chunks and 0 embeddings** (see caveat above) — no document has ever completed the pipeline, so no real search has ever had anything to search.

**Verdict: `partial`.** The code path upload → extract → chunk → embed → search → relevant results has never run end-to-end with real data. This is exactly Ticket Zero's scope (Phase 3), compounded by the upload-trigger gap above.
